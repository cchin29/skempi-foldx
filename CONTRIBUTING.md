# Contributing

Issues and pull requests are welcome — bug reports, reproducible failure cases, corrections to the
documentation, and additions to the comparator survey in [docs/PROTOCOL.md](docs/PROTOCOL.md)
especially.

## Licensing of contributions

This repository holds two things under two licences, and which one applies depends on what a
contribution touches. [`NOTICE`](NOTICE) draws the line file by file.

- **Code** — everything outside `skempi_foldx/data/` — is **MIT**. By opening a pull request
  against it you agree that your contribution is offered under MIT.
- **The computed energies** in `skempi_foldx/data/` derive from SKEMPI 2.0 and carry its
  **CC BY 4.0**, under which attribution is a licence term rather than a courtesy. That is why
  `pyproject.toml` states `MIT AND CC-BY-4.0` rather than naming either alone.

## Changes to the energies

A shipped value is not a field that can be edited. It is a function of the repaired structure and
of the whole mutation list it was computed in, so changing one record means recomputing the list
it belongs to, and a store that mixes lists is internally inconsistent in a way nothing in the
data reveals — [CHANGELOG.md](CHANGELOG.md) and [docs/VERSIONS.md](docs/VERSIONS.md) set out what
that cost in the 0.1.0 → 0.2.0 rebuild.

A pull request that edits `skempi_foldx/data/` directly will not be merged. What is useful instead
is a report: the identifier, the mutation, and what makes the value wrong. Recomputation happens
as a release, with the counts stated.

Reproducing the campaign needs a FoldX 5 licence, which FoldX issues and this project cannot
redistribute or sublicense. [docs/PROTOCOL.md](docs/PROTOCOL.md) states the settings and
[docs/DETERMINISM.md](docs/DETERMINISM.md) the evidence on what does and does not move a number.

## Development setup

There are no runtime dependencies; the suite needs `pytest`, and the release-metadata tests read
`pyproject.toml` and the CI workflow, which is why the dev extra also names `tomli` and `pyyaml`.
It names `build` as well, for the clean-tree source-distribution (sdist) check below. The
`figures` extra is separate and holds `matplotlib` and `plotly`, which only the `experiments/`
scripts that regenerate `docs/assets/` need; the suite does not, and CI does not install it.

```bash
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/python -m pytest -q
```

[docs/USAGE.md](docs/USAGE.md) covers the reader API and [docs/STORE.md](docs/STORE.md) the
on-disk layout. `tests/conftest.py` puts `experiments/` on the path, so the campaign drivers are
importable by name even though they are not part of the installed package.

Two things the suite pins that are easy to break without noticing: the shipped store's shape and
the quickstart's own values, and the agreement among every place a version or a supported range is
written down — `__version__`, `pyproject.toml`, `CITATION.cff`, the changelog's newest heading,
the README's three, the classifiers and the CI matrix. A release that moves any one of those has
to move the rest in the same commit; **Before a release** below lists them.

## Before a release

Three things CI cannot check from a clean checkout, because they are properties of the tree a
release is built from rather than of the commit:

**Build from a clean tree, and diff the archive against the commit.** `MANIFEST.in` names files by
extension rather than grafting directories, because a graft walks the filesystem and would ship
whatever running the pipeline left behind — including `rotabase.txt`, which is FoldX's licensed
support data and not this project's to redistribute. That protection is defeated by a stale
`skempi_foldx.egg-info/SOURCES.txt`, which caches the previous build's file list and is reused, so
clean first:

```bash
rm -rf build skempi_foldx.egg-info
.venv/bin/python -m build --sdist
git archive --format=tar --prefix=a/ HEAD \
  | tar t | sed 's|^a/||' > listing.txt
```

The sdist should differ from that listing only by `PKG-INFO`, `setup.cfg` and the egg-info
directory — all three generated by setuptools — and by the five git-and-CI-only entries
`.gitignore`, `.gitattributes`, `.github/workflows/tests.yml`, `.github/workflows/publish.yml`
and `.github/leakscan.sh`. `MANIFEST.in` carries no `.github` pattern, so every workflow added
later joins this list; if the diff shows one that is not named here, name it rather than
widening the check.

**Run the leak scan.** It is a script rather than a command to copy, so that what runs here and
what runs in CI cannot drift:

```bash
.github/leakscan.sh
```

Expect `clean`. The pattern must not match its own source line — that is what lets it scan
`.github/` at all — so after editing it, run the script again and confirm it still reports clean
on a tree you know is clean, and still reports a path you plant deliberately.

**Move every version declaration together.** There are seven: `skempi_foldx/__init__.py`,
`pyproject.toml`, `CITATION.cff`, the newest `CHANGELOG.md` heading, and three in `README.md` —
the install command, the pin quoted under Scope and stability, and the `Version X.Y.Z.` line that
opens it. `tests/test_version_consistency.py` fails if any is left behind, and CI additionally
refuses a tag whose name disagrees with the tree it points at.

`CITATION.cff`'s `date-released` moves with them but is **not** covered by that test, which checks
only that the date is ISO-shaped — a literal date would rot every release. Change it by hand.

Prose elsewhere says "this release" rather than the number, so these seven are the ones that move
together. Since the package installs from a git tag, the withdrawn-tag recovery command in
`README.md` names the release that *replaced* the withdrawn tags — this tree's version — so it
tracks with the rest rather than being frozen. The one pin that must **not** be bumped is the
example showing how to install the previous release, `@v0.1.0`.

`test_readme_install_pin_matches_pyproject` anchors on the *first* `pip install …@vX.Y.Z` in the
file, which is the Quickstart, because counting pins is not enough: the historical example and the
recovery command are also install commands, so a Quickstart left on the previous release still
leaves correct pins elsewhere to satisfy a count. `test_readme_git_pins_are_historical_only` then
allows any version `CHANGELOG.md` records and requires `0.1.0` to still be shown.

Push the branch and the tag together, atomically, so the tag can never point at a commit the
branch does not carry:

```bash
git push --atomic origin refs/heads/main:refs/heads/main refs/tags/vX.Y.Z:refs/tags/vX.Y.Z
```

`--follow-tags` is not enough: it declines to move a tag that already exists on the remote, and
it does not force. Note that the command above does not force either — an existing remote tag is
refused as a non-fast-forward. Moving a published tag needs an explicit lease, and the lease must
carry the expected object because a `+` in the refspec silently overrides it:

```bash
git push --atomic \
    --force-with-lease=refs/heads/main:<expected-main-sha> \
    --force-with-lease=refs/tags/vX.Y.Z:<expected-tag-object> \
    origin refs/heads/main:refs/heads/main refs/tags/vX.Y.Z:refs/tags/vX.Y.Z
```

Do that only to replace a withdrawn release, and record the prior object names first: a
force-push changes what is reachable, not what exists, and the replaced commits stay fetchable
from the host by full SHA.

**This project has no PyPI presence**, so pushing a tag is not yet the whole release: the first
upload is the one that creates the project, and that is what needs care. Registering a publisher
for a project PyPI has never seen takes a *pending* publisher, which is a different form from
adding one to an existing project — project `skempi-foldx`, owner `cchin29`, workflow
`publish.yml`, environment `pypi`.

Leave it unregistered until the tag is pushed and checked. `publish.yml` then runs every gate it
has — the ref-type and version asserts, the suite on six interpreters, the leak scan,
`python -m build`, the wheel store assertions, `twine check` — and fails only at the upload, the
one irreversible step. That is a free end-to-end rehearsal, and the red X it leaves is expected.
Register the pending publisher afterwards and re-run the failed run: same commit, same artifact,
no retag.

Whatever the README ships with must be true at upload time, because that README becomes the PyPI
project page. Today it says the package installs from a git tag, which is why the first upload has
to be its own release with its own changelog entry rather than a silent change of what an existing
release claims about itself.

## Style

Match the surrounding code: a 100-column soft limit, double quotes, and comments that say *why*
rather than *what*. Code inside fenced blocks in Markdown wraps inside 75 columns, so it survives
a narrower rendering column than GitHub's. There is no enforced formatter; please do not reformat
unrelated code in a pull request, as it buries the actual change.
